# 修正の受入確認

「テストが通った」だけでは、報告された不具合が直ったか分からない。依頼の成功条件から、観測する動作を選ぶ。

## 期待結果を実装から独立させる

仕様、ユーザーが示した例、データ契約、既存の約束から期待結果を作る。修正コードと同じ式をテストへ複写しない。仕様が不明なら、それを隠した期待値を作らず、今回の判断に必要な点だけ確認する。

例えば「ページ番号は1始まり、1ページ10件」なら、入力1で1〜10件、2で11〜20件を外から観測する。offsetの計算式をテスト側に再実装するより、既知の順序のデータと期待IDを使う。同じ値を重複して返しても件数だけでは検出できない。

## 同じ検証を変更前後へ当てる

1. 期待動作を捉える再現手順またはテストを用意する。
2. 変更前の対象で実行し、今回の不具合によって失敗することを確認する。
3. 原因と結び付く変更を適用する。
4. 同じ入力・期待値・環境で成功を確認する。
5. 変更の影響先にある正常系と境界を確認する。

これは挙動修正の基本であり、誤字修正に自動テストを新設する指示ではない。変更前を実行できない場合は、確認できた範囲を明示する。失敗ログ、終了コード、実行コマンド、対象コミットや版を追えるようにするが、秘密情報を成果物へコピーしない。

変更前後を比較するために利用中の作業を reset しない。隔離コピーや既存のworktreeを利用する。テストがネットワーク・共有データ・課金資源へ触れるなら、依頼の権限と副作用を確認する。

## 例外が消えた後の状態を見る

| 変更する処理 | 成否以外に観測すること |
| --- | --- |
| 保存・更新 | 期待値が一度反映されたか、既存値が保持されたか |
| 再試行 | 試行回数、成功・失敗時の副作用、途中成功後の再試行 |
| 集計・検索 | 対象件数だけでなくID・内容・順序、空集合や境界 |
| キャッシュ | 更新反映、対象の分離、失効後の表示 |
| 非同期処理 | 順序の違い、失敗後の状態、完了通知の対象 |

表の全行を毎回試験しない。今回変わる契約に該当する行だけ使う。テストが通っても、データ損失・副作用の重複・取りこぼしが残るなら完了にしない。

## 渡す証拠の最小単位

既存のPR説明・作業記録に次を必要な分だけ残す。単発の質問で別ファイルを作る必要はない。

```text
対象と成功条件:
変更内容と、それで直ると判断した根拠:
再現／検証コマンドまたは手順:
変更前の実測 → 変更後の実測:
保持を確認した既存動作:
反映先と、結果を左右する未確認事項:
```

コードレビュー、ビルド、単体テスト、利用者が行う操作は別の検証である。依頼された利用経路に必要な確認を選び、実行できていない段階を成功に含めない。ローカル修正だけの依頼なら本番確認を完了条件に追加しない。
